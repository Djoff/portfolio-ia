Problem

My server hosts my automations (n8n, Baserow), but I have little experience with Linux administration and security best practices. The audit confirmed it: admin access open to the whole Internet, password logins accepted, an inactive firewall, two administrator accounts and 62 pending updates.

Solution

An AI coding assistant took over the server under my supervision. It first ran a read-only audit, then proposed an improvement plan, applied step by step after my approval:

  • admin access only through a private network, with a key and no password; repeated attempts are blocked automatically;
  • an active firewall: only web traffic and the private network get through;
  • a single administrator account, with the original account disabled;
  • off-site backups checked every week, and a restore actually tested;
  • updates installed automatically every 15 days, with an alert if a task fails or does not run.

Risks & safeguards

  • Destructive AI action → the AI proposes and I approve every critical step; a full server snapshot is taken before any change.
  • Losing access to the server → every new access path is tested before the old one is closed; emergency access remains possible through the host’s console.
  • Secret leakage → no password or key is ever given to the AI: I type them myself in the terminal.
  • Service outage → scripts stop at the slightest doubt, without changing anything; n8n and Baserow are checked after every step.
  • False sense of security → a backup only counts as reliable after a real restore; an alert fires if an automated task fails or goes silent.

Outcome

In a single session, the server went from exposed to hardened, with no noticeable service interruption. It now keeps itself up to date, and I am warned if something goes wrong.

Lessons learned

AI can make up for missing technical skills, as long as I keep the decision. By approving each step, I also understood what was being done, and why.

  4. ✓ Security review

Problem

Showing my projects to recruiters without the showcase itself becoming a risk, at a time when AI-related and software supply-chain breaches are multiplying.

Solution

A bilingual static site generated by Hugo: each project is a plain text file, checked automatically before publishing. The site is designed and built with an AI coding assistant, framed by a specification, tests and a security review. Publishing is automatic: every change is tested, then put online with no manual step.

Risks & safeguards

  • Software supply chain → a single build tool with no npm dependencies; pinned versions verified by checksum.
  • Code injection (XSS) → no JavaScript, and a security policy (CSP) that forbids any script.
  • Data exposure → no forms, cookies or trackers; no internal data published, backed by an automated check.
  • AI-written code → every step is tested before it is accepted, then the whole is reviewed.
  • Publishing a broken version → publishing only happens when every test passes; otherwise the previous version stays online. The host reads the published site, with no write access to the code.

Outcome

Site live, rated A+ by securityheaders.com and Mozilla Observatory. Adding a project means adding a text file: it is online one or two minutes later.

Problem

For a second-hand seller, writing every product sheet and setting a price is slow and repetitive.

Solution

The seller sends photos of an item via Telegram. The workflow waits until the whole album has arrived, then an AI model writes the product sheet and suggests an estimate. Final prices are computed by fixed rules, the sheet is saved to a database with an internal code, and a confirmation is sent back to the seller.

Risks & safeguards

  • Unauthorised access → only authorised senders can trigger the workflow.
  • Unrealistic AI price → the AI estimates, but the final price is computed by deterministic rules.
  • Unnoticed error → the seller receives a confirmation and stays in control of the listing.
  • Leftover data → temporary album data is deleted after processing.

Outcome

Creating a product sheet goes from a manual task to simply sending photos, with a human validating.

Lessons learned

AI is excellent at describing, less reliable at pricing: combining it with explicit rules gets the best of both.

Problem

Following news from many sources takes time, and most articles are not relevant.

Solution

A scheduled workflow reads the sources listed in a Baserow database, drops articles already processed, then asks a language model to analyse each article and decide whether it is worth reading. Selected articles are grouped into a digest emailed to the configured recipients.

Risks & safeguards

  • AI misjudging relevance → every rejected article is logged with the decision, so the AI’s choices can be reviewed afterwards.
  • Duplicates → articles already sent are stored and filtered out before analysis.
  • Ambiguous silence → an empty digest is sent when nothing is selected, so you know the run happened.
  • Risky changes → sources, recipients and sending day are set in the database, without editing the workflow.

Outcome

Daily monitoring that runs on its own, with a record of every AI decision.

Lessons learned

It took seven versions: an AI agent is tuned through short iterations on real data. Logging rejections is what makes the tool trustworthy.

Automation monitoring

  • n8n
  • Telegram

When a workflow fails, an alert reaches my phone right away.

  1. Error in a workflow
  2. ✓ Error capture
  3. Telegram alert
  1. Error in a workflow
  2. ✓ Error capture
  3. Telegram alert

Problem

An automation that fails silently is worse than no automation: you believe the work is done.

Solution

A dedicated error workflow is triggered by n8n as soon as a workflow linked to it fails. It immediately sends a Telegram alert with the workflow name and the error.

Risks & safeguards

  • Silent failure → every error in a monitored workflow produces an immediate alert.
  • Blind spot → this alert does not cover an outage of n8n itself: external monitoring is still to be added.
  • Slow diagnosis → the alert says which workflow failed and why.

Outcome

Incidents are reported as they happen instead of being discovered by chance.

Lessons learned

Monitoring is not an end-of-project add-on: it is the first thing to set up before automating anything important.

  1. Topic queue
  2. Writing + web research
  3. ✓ Structured format
  4. Script document
  5. Fact-check
  6. ✓ Link check
  7. Video

Problem

Producing videos regularly for several channels takes a lot of writing, and AI-generated text can contain factual errors.

Solution

Topics go into a queue (spreadsheet). An AI agent writes the full script using web research, in an enforced format, and saves it to a document. A second workflow reviews each script: an agent checks the claims and lists its sources, and every link is tested before the script is marked as verified.

Risks & safeguards

  • Hallucinations → fact-checking is separate from writing, with sources cited for every fact.
  • Invented or dead sources → every cited link is tested automatically and its status recorded.
  • Unusable output → the AI’s answer must follow a structured format; on failure, an alert is sent.
  • Lost tracking → every topic carries a status (to do, in progress, done, verified).

Outcome

A production pipeline where each script is written, tracked and verified before it becomes a video.

Lessons learned

The first version had 26 nodes and was fragile; the simplified 17-node version is easier to maintain. Splitting “write” and “verify” into two separate agents is a principle I would reuse everywhere.
